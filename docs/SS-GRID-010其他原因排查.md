# SS-GRID-010：原生渲染档位仍失败的其他原因排查

日期：2026-10-26（Asia/Shanghai）。本轮为代码审查和隔离构造验证，不更改运行时、阈值或安装包。

后续状态：用户随后授权方向异常候选预览，现已在本地 0.2.1 实施，见 [手动校准工具评估](手动校准工具评估.md)。该后续修订还将超时检查移到一次现有候选复读之后，避免超时入口直接跳过已就绪数据。下面关于先判超时、011 只拒绝不预览的描述保留为此前诊断构建的排查记录；相机来源根因仍未确认修复。

## 证据范围

2026-10-27 后续：新收到的远端日志已经含公开 0.2.1 标识，不再只有此前 0.1.5 记录；四分之一尺寸筛选缺口与本机反射用途调研分别见 [验证记录](验证记录.md) 和 [实测报告](相机尺寸与用途实测调研.md)。本地采集修复已保留扫描时新帧、请求内观察历史并区分辅助用途，构造回归通过；尚未在受影响电脑验证。下面“当前”及旧日志描述均限定于原审查时的构建，不能当作最新实现状态。

用户转述有玩家选择“与屏幕分辨率一致”仍发生 SS-GRID-010，随后确认其使用 GitHub 公开的 0.2.0 或更早版本。暂未取得这位玩家的诊断失败组；不能将本轮发现直接宣布为其唯一根因，也不能将该反馈算作最新 0.2.1 修复后仍失败的证据。本机可读日志仍是此前的 0.1.5 记录，不替代该玩家日志。

已核对公开 0.2.0 发布提交 `1e7381d`：确实存在整段读取线程栈、读取失败跳过整条线程、超过 8 MiB 直接跳过、严格要求内部尺寸等于输出，以及 1.8 秒先判超时和重扫清空候选的实现。前两类栈扫描限制已由本地 0.2.1 的分块读取处理；短等待和候选生命周期问题在当前诊断构建中仍保留。即使尺寸完全相同，旧版的栈读取路径也可能独立触发 010。

当前 SS-GRID-010 的触发点是：定位超时，未记录方向拒绝，且**超时当时的候选容器为空**。它不代表本次请求从未找到过候选，也不表示只存在尺寸问题。

## 1. 先判超时、后读相机：冷启动和卡顿相关风险

代码中的 1.8 秒计时在 begin 的初始扫描前开始；poll 入口先检查时间，超时立即返回，不再读取候选或重扫。

存在一个确定的条件性失败路径：

1. 初次扫描恰好没有找到栈上的相机副本。
2. 游戏在后续呈现前卡顿，或初次扫描等工作占用了等待窗口。
3. 下一次 poll 到来时，相机可能已经就绪，但时间已超过 1.8 秒。
4. 读取流程尚未尝试当前数据就返回 SS-GRID-010。

这与渲染档位无关。相机初始化晚于逻辑 Settings/角色初始化，也会形成类似的短暂窗口。当前运行时通常会在关卡监测中预先完成 EXE 哈希校验，因此不把“首次磁盘哈希耗时”泛化为本版本的首要原因。

优先验证/改进方向：记录 poll 调用数、首次 poll 延迟、最大调用间隔与各次扫描耗时；等待期限应结合真实取样机会，至少避免超时入口跳过唯一一次有机会读到就绪数据的尝试。仍需保留总预算，不能无限等待或增加持续卡顿。

## 2. 周期性清空候选：SS-GRID-010 可能掩盖发现历史

每次 scan 都先清空候选；等待期间约每 250ms 重新扫描。新扫描没有命中时，之前通过验证的候选地址及其基线随即被丢弃。

因此存在以下路径：初期找到有效候选，但帧暂时没有推进；一次重扫恰好漏掉副本；超时时容器为空，最终报告 010。相机曾经出现这一事实不能从错误编号单独判断。

当前诊断中，可检查 scan 的累计 valid，以及 cache/poll 的 accepted 是否曾非零，同时 context 的 remaining_candidates 是否为零。计数只能证明曾有通过校验的候选，不单独证明它就是正确主视图。

改进方向：将“本次扫描发现的地址”和“仍待验证的已有候选”分开管理，保留有界的发现历史。是否保留旧候选参与等待，需要继续执行复读、原新帧规则、关卡验证和来源检查；不能因为曾经通过就直接采用旧网格。

## 3. 相机栈副本的存活时机没有保证

目前扫描已提交可读的线程栈范围，没有证明候选对象在扫描时仍有稳定的活动生命周期。渲染钩子还会在定位前执行 Win32/ImGui 等调用。若命中的只是先前函数留下的临时副本，后续调用可能覆盖它；不同执行路径与调度可能改变命中时机。

Windows x64 文档明确指出当前 RSP 之外的栈内存具有易变性：[x64 stack usage](https://learn.microsoft.com/en-us/cpp/build/stack-usage?view=msvc-170)。这支持“栈区域可读不等于对象仍然存活”的风险判断，**不证明现有正常样本都来自已失效栈帧**。要确认具体样本，需要生产点或活动栈范围的关联证据。

该项是当前最高优先级的来源假设。它可以解释尺寸正确、结构布局相同，却随机器或启动时机变化的失败。继续添加分辨率白名单或降低矩阵阈值不能保证补回已被覆盖的数据。

## 4. 未同步读取可能得到混合帧

读取其他线程的 960 字节参数时，当前代码没有与其写入方建立同步或完整快照协议。不能默认所有字段来自同一时刻。

本轮隔离构造验证：先构造两份各自一致的相机参数，再模拟变换矩阵已更新、其逆矩阵仍为旧值。输出尺寸保持 3840×2160，结果在 transform_inverse 分支拒绝，误差约 2.23097，远超 0.025。

这证明混合帧可以触发现有拒绝路径，不证明该玩家已发生撕裂，也不说明应把阈值放宽到接受混合帧。优先取得参数生成/上传完成后的快照；双次读取一致性检查只能降低风险，不能代替正确的同步和生命周期证明。

## 5. 一个明确的字段类型处理问题

反射资料表明 Viewpoint_Params 偏移 860 的 vp_auto_tbn 是 int32。自检前的实现却将 f[160] 到 f[223] 整段作为浮点数做有限值/范围检查，其中包括 f[215] 对应的这个整数。

隔离验证仅把该整数的位模式设为 -1，其他相机数据不变：修复前报告 camera_values、bad_index=215。原因是整数位模式被解释为浮点 NaN，而不是矩阵损坏。

**已确认检查方式与字段类型不符，但尚未确认游戏会为该字段写入 -1。** 已有正常样本中观察到的值是 0。2026-10-26 自检修复：正式校验及仅用于诊断的视口探测都跳过这个不参与网格计算的整数字段，其他浮点/矩阵/方向/新帧检查保持。没有凭空限定其合法整数枚举；后续若要用它判定渲染用途，必须先取得实际含义和取值证据。回归覆盖 -1、浮点 NaN/Inf 对应的整数位模式可通过，相邻真正浮点字段的 NaN 仍被拒绝。该类型修复不宣布为该用户现场根因。

## 6. 原生渲染设置不能排除的其他状态

- 地图量检查独立于尺寸。只要 map_amount 非有限或大于 0.05，候选仍会被拒绝。已有真实地图样本的 type=8、map_amount=1，不能仅凭主视图用途或分辨率设置放行。
- 旧副本、零帧号、方向/逆矩阵数据异常都会在尺寸正确时失败；需要看具体拒绝计数。
- 窗口、DPI、黑边或其他渲染路径下，用户选项名称与读到的实际视口是否一一对应仍待验证。构造内部 3072×1728、输出 3840×2160 时，当前模式筛选会拒绝。这个构造只说明未知比例仍会失败，**没有证明某台机器的 DPI 确实会产生这组尺寸**。
- 公开 0.2.0 或更早构建仍包含旧的整段栈读取与 8 MiB 跳过逻辑；较新诊断包已改为分块读取。因此受影响构建版本会直接改变优先排查项。

## 7. 暂不支持“普通浮点误差普遍超限”的结论

对正常相机作一致的世界坐标平移，在 64～8192 单位的若干测试点上，当前校验全部通过；观察到的最大单精度变换逆误差为 0.00390625，低于 0.025，参考点屏幕偏差最高约 0.0222 像素。

这只是有限构造，不能证明其他姿态/场景都不会超过阈值，但没有为“普通硬件浮点差异就普遍导致 010”提供证据。双精度重算残差也不保证结果更小：输入矩阵本身已存为单精度。缺少现场数据时，不优先放宽原阈值。

## 8. 如何用现有诊断缩小范围

| 日志线索 | 优先调查 |
| --- | --- |
| stacks=0 或 bytes=0 | API/线程查询、栈范围及读取问题；查看 scan_access 的具体计数和状态 |
| 出现 accepted/valid，最后 remaining_candidates=0 | 发现历史被重扫覆盖、候选存活时机；不能直接称为从未发现相机 |
| 扫描很少、elapsed_ms 已超时，后续阶段计数很少 | 冷启动等待窗口/卡顿；仍需 poll 调用数等时序量区分具体情况 |
| camera_values 且 bad_index=215 | 来自自检修复前构建的整数字段误作浮点检查；核对实际整数位模式与构建版本 |
| transform_inverse/projection_inverse | 分辨正常残差、混合帧或错误来源；查看样本误差与其他字段，不立即降阈值 |
| map_amount | 地图/过渡或错误副本，与分辨率设置分别排查 |
| 只有 viewport_probe 留下样本 | 以实际 render/output 数值核对模式、DPI/窗口/合成假设，不能只看菜单选项 |

EXE 哈希不符在当前代码应报 001，关卡/角色读取失败应报 002～005，投影失败报 007～009；这些不应泛泛地列为当前 010 的同等原因。011 则表示本次曾识别到方向异常候选，含义与 010 也不同。

当前建议优先级：**来源存活/读取时机、短等待与重扫生命周期 → 现场混合帧或字段类型证据 → 实际视口映射 → 经数据证明的数值阈值问题。** 本轮没有认定新的唯一根因，也没有声称该用户已修复。

## 9. 同一玩家从 0.1.2 上下翻转变为后续版本 011

用户进一步反馈：同一玩家在 0.1.2 看见网格上下翻转，后续版本提示方向异常并拒绝定位。这支持“原异常仍存在，新增保护阻止显示”的连续性假设；尚无该玩家同一现场的矩阵和主视图关联证据，不能据此直接认定唯一根因。

方向保护只解决拒绝异常数据。镜像变换及其配套逆矩阵仍可以互为逆，旧的逆矩阵校验不会单独排除它；当前方向校验将这类构造拒绝。它没有保证一定能找到正确主视图，也没有从来源上消除异常。最新本地 0.2.1 的渲染档位和栈读取修复不能作为该玩家上下翻转已经修复的证据。

011 的报告还有一个限制：本次请求中，只要 scan/cache/poll 任一阶段出现方向异常，就记住该标志；1.8 秒超时时，该标志优先于“候选为空”和“未取得新帧”决定最终错误。因此 011 只证明曾经遇到异常候选，不能证明所有候选都异常，或被拒候选就是当前屏幕的主相机。可能同时存在正常但静止的副本、漏扫或超时问题。

需要区分的两条路径：

- 错误来源或失效副本：找到其他渲染用途、旧数据或不一致的数据；应加强生产点、用途、生命周期与最终呈现视图的关联，不能单靠尺寸和新帧排序。
- 合法视图不符合当前方向假设：当前要求向下观察、XY 投影朝向为正、世界 +Z 朝屏幕上方。现有覆盖证明正常斜俯视和水平旋转可通过，未覆盖所有相机俯仰、滚转及渲染合成路径，不能排除误拒。应先取得来源和最终屏幕映射证据，再决定坐标转换或支持范围。

2026-10-26 使用当前头文件重新编译并回放既有样本：主世界斜俯视、地图返回、小关卡重入共 6 份正常样本全部通过；额外研究快照 128 份中 122 份通过、6 份其他校验失败、没有方向拒绝。这不是新的游戏实测，也没有包含该玩家的倒置现场，不能证明不存在误拒。

现有诊断已记录 direction_z、handedness、world_up、矩阵误差及各阶段累计计数，可先判断触发的方向条件与是否同时出现正常候选。单一标量样本仍不足以判明主视图身份；后续来源诊断应关联同一候选的用途与连续采样，避免将多个副本误作独立置信证据。不要直接对矩阵取反、关闭方向保护或以较高置信分绕过方向问题，否则可能恢复 0.1.2 的倒置网格。

# 错误反馈方式评估

日期：2026-10-29（Asia/Shanghai）。按用户要求比较邮箱反馈与 GitHub Issues 提交接口；结论为当前以邮箱为主，GitHub 网页入口可作为后续补充。

## 当前采用的操作

报错后点“汇报错误”，先用默认 Shift+G 或当前自定义按键检查相机。仍无法检测或贴合时，点一个按钮“打开游戏目录并复制邮箱”：从正在运行的游戏 EXE 路径取得实际安装目录，打开该目录，并先把 `xlwpy@qq.com` 复制到系统剪贴板。玩家自行将 `StarSketch.log` 作为邮件附件发送。

该功能没有接入邮件 API，不要求配置默认邮件客户端，不读取、复制或上传日志内容，也不自动发送邮件。先复制再打开目录，避免资源管理器切换焦点后遗漏复制；两项独立执行，部分失败仍保留另一项成功，并显示具体提示。工作在持有 DLL 引用的短时后台任务中，绘制线程不等待 Shell 调用，退出时不 join。

同日新增“一键复制诊断信息”：在本地生成分辨率、窗口/Windows/显卡/驱动、插件版本、关卡及原错误/当前状态的文本，再复制到剪贴板供玩家粘贴到邮件正文。不读取日志，不复制内存地址、矩阵、标注、用户名或安装路径。日志仍由玩家附上。此功能与邮箱按钮共用串行后台任务和独立成功/失败提示，未接入 GitHub API。

## 方案比较

| 方案 | 玩家操作与门槛 | 维护侧体验 | 接入成本 |
| --- | --- | --- | --- |
| 邮箱，打开目录并复制地址 | 用现有邮箱发日志附件；无需另行进行 GitHub 授权 | 适合少量个案及私下交换日志；整理、去重和跟进由维护者完成 | 当前目录/剪贴板辅助即可，无邮件 API 或服务端 |
| GitHub 网页 Issue | 用 GitHub 账号提交，可预填版本、错误编号和检查结果，再拖入日志 | 集中讨论、状态、标签、关联修复与重复问题更方便 | 增加网页链接/模板即可，应用无需持有写入 Token |
| DLL 直接调用 GitHub Issues API | 需要用户认证/授权，或另建接收反馈的服务端中转 | 可以形成结构化问题，但需处理认证、失败和滥用 | 明显高于当前邮箱方案，不应把维护者的个人 Token 内置进可分发 DLL |

GitHub 官方创建 Issue 接口使用 `POST /repos/{owner}/{repo}/issues`，支持 GitHub App 用户/安装令牌及细粒度个人令牌；细粒度令牌需要 Issues 写入权限。创建参数主要是标题、正文及问题元数据。见 [REST 创建 Issue](https://docs.github.com/en/rest/issues/issues#create-an-issue)。

网页方式支持通过 URL 预填标题、正文等字段，仍由玩家检查后提交，见 [通过 URL 创建 Issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue#creating-an-issue-from-a-url-query)。日志可拖入网页评论框；当前官方列出 `.log`、`.txt` 等支持类型。公开仓库的附件无需认证即可访问，所以它不等同于向邮箱私下发送日志。见 [GitHub 附件规则](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files)。

建议当前按用户确定的邮箱方案交付。若反馈量增加，再加可选的 GitHub 网页 Issue 入口；直接 REST API 暂时没有足以抵消认证/维护成本的收益。本次没有创建 Issue、发布内容或发送任何反馈邮件。

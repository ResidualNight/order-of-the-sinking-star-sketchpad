# 相机尺寸与用途实测调研

日期：2026-10-27（Asia/Shanghai）。本轮为用户授权的游戏安装目录检查、游戏内设置切换及外部只读采样；没有修改运行时源码、安装 DLL 或发布附件。

## 结论

相机视口与输出画布之间确实还存在 1/6、1/8、1/12 等关系。本轮这些小尺寸数据都来自与反射用途对应的 `type=5` 视图，不能据此要求自动定位全部放行。反射视口跟随场景内部渲染尺寸和画质，而非始终跟随最终窗口尺寸。

此前四分之一修复补上了尺寸筛选缺口，但没有证明远端日志里的 960×540 候选就是正确主相机。此次本机“超高性能 + 4K 原生”实际产生了同样尺寸、同样方向类别 3 的反射候选，这是相似现场，不能代替对方机器的来源确认。

同尺寸、同帧号、矩阵自洽、帧推进以及 `type=8` 中的任何单项，都不足以证明是当前支持的普通游戏主视图。后续应补充来源/用途诊断和有效主视图的采集稳定性，保留矩阵、新帧、地图、关卡及用户确认边界。

## 方法与范围

- 本机游戏 r67271，EXE SHA256 为 `0ae10a513dae25286fe93d0db4fa8a2df9a473bc07e1734e12bc1ad30166db1c`，与既有反射 schema 对应。
- 物理输出为 3840×2160，单机、单个主世界位置。通过菜单方向键及 Enter 切换画质和渲染档位；没有移动角色、加载其他战役或写入游戏内存。
- 外部诊断仅以查询及读内存权限打开该游戏，校验进程镜像路径，扫描线程栈中已提交可读的非 guard 区域。每个状态三次扫描，间隔 100ms；单栈有 64MiB 上界，最多保留 2048 个结构近似样本。它是独立诊断程序，不是插件扫描耗时或完整性基准。
- 诊断发现阶段允许更广的内部视口，仅用于调查；保持方向单位长度、正帧号/时间、有限变换及变换逆残差等结构预筛。比较其余正式检查时，暂以物理输出倒数替代内存中视口两个字段，分别报告“尺寸是否被接受”和“其他检查结果”；该替代仅在外部程序的堆上副本中发生，不写游戏、不参与插件采用。
- `fresh` 只计入复读后尺寸相同、其他相机校验合格（允许方向异常）且满足原新帧规则的来源。地图样本 fresh=0 不代表相机没有更新，而是它们未通过地图检查。
- 只保存尺寸、原始用途值、方向类别、校验原因、计数、帧范围及有限投影差值。地址和完整相机矩阵仅在诊断进程内存中短时存在，没有写入报告或磁盘。原始游戏日志不加入仓库。
- 标量结果与诊断源程序在忽略目录 `work/camera-relations-20261027/`。没有进行跨设备、超宽屏、其他关卡、阴影 pass、自定义分辨率或截图模式的实测。

## 静态资料

本版本 `Viewpoint_Params` 大小为 960 字节，偏移 864 是 `vp_framebuffer_inverse_extents`，偏移 904 是 uint32 `type`。后者的反射字段类型不是枚举，不能仅凭字段类型宣称用途绑定已得到完整证明。

`View_Kind` 枚举含 `REFLECTION=5`、`MAIN_VIEW=8`，另有动态/静态/聚光/立方体阴影、岸线、烘焙、光探针等用途。本轮受控切换时，type=5 的尺寸随游戏图形日志中的 reflection_width/height 同步变化，方向类别均为 3；type=8 存在正常和地图视角。这比单独比对枚举数值提供了更强的用途证据，仍不是所有用途或所有版本的验证。

`Render_Resolution` 包含 Fixed_720p、Fixed_1080p、Fixed_1440p、Fixed_4k、Display_Size_Halved、Display_Size，以及 Custom、Custom_Screenshot、Automatic。后三者仅确认存在定义，没有确认普通玩家菜单会提供或当前运行会启用。

`Graphics_Settings` 独立保存 reflection_width、reflection_height 和 reflection_count。受控切换的游戏图形日志与采样尺寸相互印证。

本轮 11 个设置组合中，采到的正常主视图尺寸均由当前已有规则覆盖。没有证据要求为了正常主视图新增 1/6、1/8 或 1/12 的自动白名单。反射视图通过尺寸门后仍属于方向异常候选；“尺寸接受”不等于运行时无条件自动采用。

以这些观测为限，反射尺寸可表达为 `内部场景尺寸 × 画质缩放`：画质为 1、平衡/性能为 1/2、超高性能为 1/4。若内部场景又是输出的一半，超高性能反射相对输出就是 1/8；固定内部档位也会产生 1/6、1/12 这类分母。这里不是对所有设备、场景和取整规则的完整公式证明。

## 不同尺寸、不同用途与投影

在菜单外的“画质 + 720P”状态，既采到 1280×720、type=8 的当前场景数据，也采到 3840×2160、type=8 的更新副本。对相机前向射线与 z=1 平面交点附近九个世界点，统一映射到完整输出画布，二者屏幕投影差为 0。至少本组样本中，内部尺寸不同并不代表投影不同；不能只按尺寸把它们认作不同主相机。

同次采样的 type=5 反射视图，在 z=1 保持相同世界点/高度时，对四种完整屏幕翻转选择误差最小的一种，九点中的最大投影差仍约 146.154 像素；直接把反射高度改为 -1 后，同法差值仍约 14.366 像素。恢复原生画质后的另一组观测分别约为 273.524 和 27.677 像素。

这些是两个实际相机之间的数值差，不是与截图地砖标注比较得到的准确率或全屏最大误差。它们说明反射并非只需屏幕翻转即可保证恢复主视图；还涉及反射平面/高度及投影关系。本轮没有求解或确认反射平面，不能把简单高度取负作为通用修复，也不改变现有手动翻转、高度调整和用户确认流程。

## 地图与 DPI

在“画质 + 720P”进入地图时，采到 type=8、map_amount=1 的 1280×720 数据，以及 1024×1024 的结构近似副本。即使 type=8 且尺寸匹配，也应继续受地图检查拒绝；方形数据也不能单凭尺寸直接归为阴影相机。

最初外部诊断进程未声明 DPI 感知，GetClientRect 得到 2560×1440；仅将诊断自身线程临时设为 Per-Monitor V2 后，得到 3840×2160，与游戏图形日志一致。后续全部尺寸表均使用物理尺寸。没有修改游戏的 DPI 上下文，也没有据此外推插件存在 DPI 缩放错误；该现象说明测量程序也必须交代坐标单位。

## 对远端 010 与后续实现的影响

1. 远端 960×540、方向类别 3 的样本与本机超高性能反射视图高度相似，但远端旧诊断没有 type、当前渲染/画质及来源关联，不能宣称已确认同一来源。
2. 远端原尺寸副本的投影逆错误、float slot 178 异常仍须拒绝；本轮没有证明它们是可安全绕过的字段，也没有确定其不完整/被覆盖的具体原因。
3. 优先在有限诊断样本中加入 raw type、主/反射尺寸关系及采样时序证据。再用完整、鲜活的 type=8 数据作优先来源研究；不把 type=8 当作放行充分条件。
4. 反射数据若保留在临时选择器，应明确作为需检查的辅助视图。不能因尺寸匹配、矩阵可逆或有新帧，就提高其自动可信度；不能覆盖用户的显式确认与会话网格保留要求。
5. 若需让手动恢复覆盖更多反射尺寸，应按已经确认的“内部场景尺寸 × 反射画质关系”单独评估，保持数值/新帧/投影/地图/关卡检查，并验证网格贴合。不要直接把所有等比例尺寸加入自动白名单。
6. 已安装及公开构建没有更改；本轮也没有将本地 quarter 包安装到游戏。因此本机采样不构成 quarter 修复包的游戏内网格验收，更不能替代受影响机器复测。

## 环境恢复

结束采样前，界面恢复为全屏开、垂直同步开、帧率上限 144、分辨率与屏幕一致（4K）、图形模式画质、多重采样自动（开），与启动时一致。最终图形日志的 Quality 配置及只读采样均恢复 3840×2160 的主/反射视口。

游戏通过自身菜单正常退出；没有强制终止。调研过程中没有重装或更新 DLL，没有新增运行时持久化字段，没有上传原始日志、内存或游戏资源。

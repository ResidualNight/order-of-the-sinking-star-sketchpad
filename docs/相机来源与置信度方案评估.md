# 相机来源、候选评分与跨设备鲁棒性评估

日期：2026-10-26（Asia/Shanghai）。状态：方案评估，不更改当前识别规则，不实施新 Hook。

后续状态：本评估早于同日用户授权的版本哈希警告化、方向异常预览以及手动工具调整。当前代码的方向选择不是相机身份偏好；用户提出候选列表和跨关卡相似匹配后，补充了 [相机列表与跨关卡匹配评估](相机列表与跨关卡匹配评估.md)，其中包含旧样本粗特征不唯一的回放结果。新列表、相机特征持久化和自动学习尚未实施；下面的早期硬门槛建议不替代后续用户授权。

## 结论

建议采用“有明确来源的主视图数据 + 必须满足的安全检查 + 多帧候选评分 + 独立坐标映射验证”。

置信度可以帮助挑选相机、处理合理范围内的数值差异，但无法从未发现的数据中恢复相机，也不能仅凭高分把反射相机、地图相机、旧副本或错误高度层变成可用网格。应优先减少对瞬时线程栈副本的依赖，再校准自动采用门槛。

不同机型、分辨率和窗口设置是验收主轴。源数据识别与网格在屏幕上的贴合精度分别评估，不能只统计“是否找到了矩阵”。

## 1. 当前实现和已核对的证据

- 当前读取器仅在精确游戏 EXE 哈希及运行布局校验通过后工作。从线程栈发现 960 字节 Viewpoint_Params，校验矩阵、方向、地图量和视口，并等待帧号/时间推进。
- 现有 Grid.confidence 在自动相机投影成功后直接设为 1，属于“通过当前校验”的标记，不是经过样本校准的正确概率。旧图像诊断另有纹理评分，也不能直接用于相机可信度。
- 先前研究已发现许多堆内常量缓冲副本不更新，扩大到全进程/全堆扫描会增加旧副本、其他视图和扫描成本，不能自然解决来源问题。
- 新线索：本地反射资料中的 Viewpoint_Params 在偏移 904 有 uint32 type 字段；视图用途枚举中 MAIN_VIEW 对应 8，并存在反射、阴影等其他用途。主世界正常斜视、地图返回和小关卡重入的 6 个已有样本，其该字段均为 8。**两者语义对应仍是假设，需要反射/阴影等负例验证**，不能立即把 type=8 升格为充分条件。
- 已保存的完整地图样本同样包含 type=8，且 map_amount=1。这直接说明：即使该字段表示主视图，“主视图”也不等于“当前支持自动网格的普通游戏视角”。
- 当前相机投影使用 DX12 backbuffer 尺寸，UI 画布使用 Win32 后端 GetClientRect 得到的 DisplaySize。两者在现有测试中相符，但不同 DPI/窗口模式下是否始终相符尚未验证。仓库内 ImGui 1.91.9b 的 DX12 后端也直接使用 DisplaySize 设置视口，应整体审计，不能只改网格公式。

这些是代码/历史样本的核对结果，不代表完成了新硬件、黑边、超宽屏或混合 DPI 实机验证。

## 2. 可选的相机获取方式

| 方案 | 收益 | 主要限制 | 建议定位 |
| --- | --- | --- | --- |
| 从已验证的游戏根对象追踪当前 Viewpoint_Params 持久实例 | 不依赖临时栈帧；已知地址可低成本读取，易做完整性检查 | 还没有证明存在可稳定追踪的当前实例；须验证生命周期、版本和类型归属 | 优先研究 |
| 在相机参数生成/上传位置取得完成后的快照 | 取得时机明确，减少跨线程读到半更新数据的风险 | 需定位函数并证明主视图用途；游戏代码 Hook 的兼容、重入和退出风险高于只读指针链 | 根对象路线不可行时考虑 |
| 跟踪 DX12 主场景实际绑定的相机参数 | 能将参数与正在绘制的场景、视口和渲染目标关联；来源证据强 | 要处理 root CBV、描述符表、根常量/其他缓冲路径，以及多命令列表、多 pass、资源复用和帧提交关系 | 有潜力的后续验证路线，先做受限原型 |
| 保留栈扫描，增加用途识别及多帧排序 | 改动相对小，可以利用已有诊断快速改善 | 相机不在栈上、出现太短或读取撕裂时仍会漏；评分无法修复这一点 | 过渡与受限后备 |
| 扩大堆/全进程模式扫描 | 可能增加召回候选 | 旧副本和非主视图更多，成本及误识别面都增加 | 不作为默认策略 |
| 图像网格识别 | 能独立检查部分屏幕贴合线索，较少依赖游戏布局 | 装饰、纹理、光影、遮挡和透视易造成错格；旧算法已有相关局限 | 诊断或用户确认的辅助方式，保留手动校准 |

DX12 提供常量缓冲绑定和视口设置接口，但绑定中的 GPU 虚拟地址不能直接当作 CPU 指针读取。需要追踪资源及偏移；CPU 读上传内存可能代价较高，GPU 回读又需要正确同步，不能在绘画热路径增加阻塞。仅观察最后一次绑定也不足以确认主场景，因为同一帧包含多种视图和 UI pass。参考：[根常量缓冲绑定](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-setgraphicsrootconstantbufferview)、[视口设置](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-rssetviewports)、[资源 Map 限制](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12resource-map)、[GPU 回读与同步](https://learn.microsoft.com/en-us/windows/win32/direct3d12/readback-data-using-heaps)。这些接口说明不证明本游戏实际采用哪条绑定路径。

Camera_Control 的设计参数可作为 FOV/用途等辅助信息，不能直接替代当前相机：运行时平移、摆动、过渡和地图插值可能使静态实体姿态与当前视图不同。

## 3. 置信度的正确用途

### 3.1 分别判断三件事

1. 候选是否是结构完整、可用于计算的相机数据。
2. 是否对应当前正在呈现、且本功能支持的主场景视图。
3. 高度层、输出映射和屏幕坐标是否足以生成可用网格。

不同候选地址若包含同一帧、同一参数副本，应按相机身份/内容关系归组；不能把多个复制品算成多份独立证据，也不能因此误认为存在多个同样可信但互相竞争的视图。

### 3.2 必须拒绝的情况

精确版本/布局未验证、读取失败、非有限或不可用矩阵、跨关卡混合状态、明确的镜像/倒置、当前不支持的地图状态、不可确定的输出映射和退化网格，继续拒绝自动吸附。高分不能抵消这些失败。失败后保留几何预览并暂停自动吸附/染色，手动校准继续可用。

相机用途字段只有在受控实验确认含义后，才可作为必要条件或强来源证据；目前不直接使用数值 8 放行。

### 3.3 适合连续评分的证据

| 证据组 | 可评估内容 | 跨设备处理 |
| --- | --- | --- |
| 来源和用途 | 来自已验证对象链、完成的参数生产点或主场景绑定；用途与当前状态一致 | 依据语义和当前资源关系，不依赖绝对内存地址、线程编号或第几个 GPU 缓冲 |
| 时间关联 | 候选与当前呈现阶段关联，连续观测一致，能够识别旧副本 | 结合真实经过时间、呈现序列和实测延迟；避免把所有机器固定成同一帧差门槛 |
| 数学一致性 | 变换/逆变换残差、方向长度、投影回代误差及数值条件 | 评估双精度复核、尺度相关残差和屏幕像素误差；原始残差仍保留，不以归一化掩盖病态矩阵 |
| 视口与网格解释能力 | 内部渲染、场景视口、最终输出关系一致，所选高度层可生成合理格网 | 基于实际视口和映射，尽量减少固定分辨率白名单依赖；高度层置信度单独处理 |

矩阵可逆、逆矩阵一致、方向近似单位长度等证据相互相关，不能简单相乘成“正确概率”。稳定的反射视图或旧快照也可能同时满足它们。角色投影是否接近可见区域只能作弱证据，不能要求所有角色都在屏幕内。

静止镜头的矩阵完全不变是正常情况。若数据来源能证明本帧仍在使用这组参数，不应仅因数值不变就判为旧相机；而没有来源证明的栈副本，需要更保守的时序验证。双次读取一致可以降低撕裂风险，但不能替代对生产点和同步关系的证明。

### 3.4 分数与阈值

建议初期将分数称为“候选评分”，范围 0～100。发布阈值由已标注样本校准，不能直接宣称 90 分等于 90% 正确。

如需要原型观察线，可暂定：满足全部必要条件、评分至少 85、比次优的不同视图至少高 15 分、连续 3～5 个有效观察帧一致。**这些数字只是实验起点，没有数据证明可直接用于发布自动采用。** 某些观察帧来自同一内容副本时不能重复加分。

通过迟滞减少候选来回切换，但必要条件失败、关卡/坐标映射失效时立即暂停自动功能。不能靠迟滞继续使用已失效的旧网格。

影子评分阶段只记录分项、排名、拒绝原因和最终人工标签，不改变原采用结果。验证集按机器/关卡/窗口设置分组留出，避免把同一机器相邻帧随机拆分，造成虚假的高准确率。即使测试集没有误采纳，也要报告样本量和覆盖范围，不能宣称总体误判率为零。

## 4. 分辨率、窗口和 DPI 的独立映射

需要明确以下链路：

```text
世界位置与选定高度层
  → 主视图矩阵与 NDC
  → 场景实际 viewport（含原点、宽高）
  → 缩放/裁剪/黑边等合成关系
  → swapchain 的物理像素
  → UI 画布与鼠标输入坐标
```

普通全屏填充的情况可简化为 NDC 直接映射完整输出。不能把这个特例默认为所有窗口和机型都成立。

- 内部 720P 与输出 4K 可以完全合法；内部 4K 与输出 1080P 也可以合法。
- 窗口任意拖动可能产生 1365×767 等非整齐尺寸；不能靠“是否常见分辨率”判断相机真假。
- 16:9、16:10、21:9、32:9、非零视口原点和黑边需要实际映射证据。发现黑边时不能把场景强行拉满整个窗口。
- Windows 100%/125%/150%/200% 缩放、不同 DPI 显示器之间移动窗口，要确认所有坐标的单位和调用线程 DPI 上下文。不要为修复插件而擅自更改游戏进程的全局 DPI 感知模式。
- 窗口、无边框和独占全屏（游戏/系统实际提供时）之间切换，以及 swapchain/资源重建，应更新映射代次并丢弃未完成的旧结果。
- 最小化、零尺寸、Alt+Tab、恢复、跨屏移动和拖动调整期间允许短暂不可用；恢复稳定后应自动重新验证，避免整场持续失败。

Windows 确实可能对部分 API 返回值执行 DPI 虚拟化，因此客户区尺寸和物理像素的等同关系需要核实：[Microsoft 高 DPI 指南](https://learn.microsoft.com/en-us/windows/win32/hidpi/high-dpi-desktop-application-development-on-windows)。DXGI 的窗口/全屏状态和缓冲调整也是独立状态：[D3D12 swapchain 说明](https://learn.microsoft.com/en-us/windows/win32/direct3d12/swap-chains)。这表明需要审计当前假设，并不等于已经在本项目复现 DPI 错位。

建议每个结果关联当前关卡、相机来源、swapchain/缓冲和坐标映射的代次。请求完成前后这些代次不一致，则拒绝结果。标记仍保持屏幕固定，不随相机移动，不保存草稿或校准几何。

## 5. 鲁棒性验证范围

| 维度 | 代表覆盖 |
| --- | --- |
| GPU 与机器 | NVIDIA、AMD、Intel；独显、核显、混合显卡笔记本；低性能和高刷新率设备 |
| 系统与运行环境 | 明确支持的 Windows 版本、可取得的不同驱动版本；干净环境与常见叠加层组合 |
| 输出尺寸 | 720P、1080P、1440P、4K；16:10、超宽屏；奇数与连续变化的窗口尺寸 |
| 内部渲染 | 全部六个公开档位；内部小于、等于及大于输出；自定义模式仅在映射已验证后考虑 |
| DPI 与显示器 | 100%、125%、150%、200%；同 DPI 与混合 DPI 双屏、跨屏移动 |
| 窗口状态 | 实际可用的全屏/无边框/窗口；最大化、拖动、最小化恢复、Alt+Tab |
| 时序 | 冷启动直接读到保存的非原生渲染档位；30/60/高帧率及卡顿；静止镜头、暂停、加载与恢复 |
| 场景 | 主世界、小关卡、地图进入/退出、多高度角色、镜头过渡、反射/阴影视图负例 |

先使用参数化合成测试覆盖尺寸、DPI、视口偏移、数值扰动、不同帧延迟和资源代次。再使用代表性硬件的两两组合覆盖，并重点实测高风险组合：4K+150%缩放+1080P内部渲染、超宽窗口+固定渲染档位、混合DPI跨屏、低帧率冷启动、显卡切换/资源重建。

合成坐标测试不能替代真实驱动和游戏渲染测试。一台机器调分辨率也不能代表三家显卡与混合显卡都已覆盖。现阶段这些都是计划，不宣称已经通过。

验收分别记录：

- 正确主视图识别成功率与初始化耗时，特别区分冷启动和运行中切换。
- 误采纳非主视图、地图、镜像或旧副本的次数；这类错误优先于漏检控制。
- 同一高度平面上可识别参考点的屏幕偏差，以物理像素和格距比例报告，不用“看起来差不多”替代。
- 状态切换后的恢复时间、旧结果是否被正确暂停，以及标记是否继续保持屏幕原位。
- 采集/评分的 CPU 开销、帧时间增量及尾部延迟；热路径避免全内存扫描和等待 GPU 回读。

样本中“模型投影与同一矩阵的直接计算一致”只证明代数实现，不能当作实际地砖/角色在屏幕上的贴合精度。

## 6. 建议推进顺序

1. 用现有诊断先区分来源缺失、读取撕裂、尺寸映射、数值临界与帧序列问题；补充视图用途的对照实验，不直接改变采用门槛。
2. 优先寻找被主场景实际使用的 Viewpoint_Params 对象或完成的生成/上传位置。验证持久指针链是否可行，再决定是否需要游戏函数或 DX12 层 Hook。
3. 同步审计内部视口、最终合成、backbuffer、Win32/ImGui 和鼠标坐标链，建立带代次的显式映射。这个工作不应等到评分完成之后。
4. 以影子模式比较来源与候选评分，保留现有识别和手动回退；只保存有限诊断量，不加入完整矩阵/内存或画面采集。
5. 在按机器和显示配置留出的样本上校准分数与门槛。达到约定的误采纳、贴合、恢复和性能要求后，再启用自动采用。

本轮仅形成评估文档，未改变运行时、安装包、游戏设置或已安装 DLL，未发布 GitHub。
